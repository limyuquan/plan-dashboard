The server (server/) reads the docs folder into a tree of tasks, phases and docs, watches it, and pushes events to the browser. The web app (web/) never parses paths itself: it shows the tree it is sent and keeps every pane change inside one pure, tested module. shared/ holds the types and the config schema both sides use.

How a request moves

A new plan reaches your screen without a refresh

Write, settle, rescan, ring, show. A 400 ms wait lets an agent finish writing before anyone is told.

  1. An agent writes phase-2-…/plan.html into the docs folder.

    Nothing in the dashboard is called; the file simply appears.

  2. The watcher collects the change and waits for writes to settle.

    Adds and edits are gathered, and a 400 ms timer restarts on every event, so a page written in chunks is announced once.

    server/docs.ts:104server/docs.ts:109
  3. The folder is rescanned into a tree.

    Each file is placed in its task and phase using the configured folder names and phase pattern.

    server/docs.ts:86server/scan.ts:53
  4. The server rings: tree, then added.

    Events go out over a server-sent event stream to every listening tab.

    server/docs.ts:93server/routes/events.ts:5
  5. One browser tab holds the stream and relays it to the others.

    A Web Lock picks the tab and a BroadcastChannel passes events on, so many tabs do not use up the browser's connections.

    web/events.ts:9
  6. The app refreshes its tree and raises a "new plan" toast.

    The toast names the task and phase, with a button that opens the phase as a workspace.

    web/state/tree.ts:78web/state/workspaces.ts:104
  7. A pane loads the file in an iframe from /docs/.

    HTML is sent as written; Markdown is turned into a page in the dashboard's theme first.

    server/routes/files.ts:46server/markdown.ts:107
  8. The bridge wires up the page.

    Links open as tabs, scroll is remembered, and the theme is handed in by postMessage.

    web/viewer/frame.ts:35

How does settle / restore work?

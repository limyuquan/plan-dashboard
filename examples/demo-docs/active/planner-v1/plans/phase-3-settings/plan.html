Implementation plan·Phase 3 of Planner v1·configurable folder conventions

Your folder layout becomes a setting, not a code change

Today the dashboard only reads one folder shape: active/ and done/, a plans/ folder, phase-1-… folders, and a fixed list of file names. This phase moves every one of those rules into a single JSON file with a settings page on top, so the dashboard reads the folder you already have. The browser stops guessing where a doc belongs; the server tells it.

Written before implementation, from the phase brief and the code it hooks into: shared/config.ts, server/config.ts, server/scan.ts, server/routes/config.ts, web/settings/. Line references point at the tree as it will look once built; counts from wc -l and grep -c "it(".

What changes

A schema, a store, a reader that follows it, and a page to edit it

One schema is the source of truth: the server validates with it, the settings page edits it, and the scanner reads through it.

A · shared
shared/config.ts zod schema, defaults, wildcard matcher. 105 lines.

Every rule above becomes a typed key. configSchema (shared/config.ts:50) is .strict(), so a misspelt key is an error, not a silent no-op. A phase pattern must compile and must contain (?<num> (shared/config.ts:7, :59). DEFAULT_CONFIG (shared/config.ts:71) spells out today's layout, so nothing changes for existing users. withDefaults (shared/config.ts:95) lets a file hold only the keys it changes. Doc type patterns use * and ?, not regex (shared/config.ts:99).

A · server
server/config.ts ConfigStore: load, save, watch. 82 lines.

The file on disk, plus this run's flags. The path is ~/.config/planner/config.json, or under $XDG_CONFIG_HOME (server/config.ts:7). current merges the saved file with --root/--port (server/config.ts:23); stored returns the file alone, which is what the settings page edits (server/config.ts:29). Saves write a temp file and rename it (server/config.ts:57). Hand edits are noticed by watch() (server/config.ts:67).

Each doc gets its kind from kindOf (server/scan.ts:50) and its workspace key ws (server/scan.ts:74). The same pass fills the preview counts the settings page shows (server/scan.ts:59).

The browser stops re-deriving the folder rules

Before

The client splits each doc's path on / to work out its task and phase. That is a second copy of the layout rules, and it breaks the moment the layout changes.

After

The server already knows where each doc sits, so it sends ws with every doc (server/scan.ts:74). The client reads doc.ws (web/state/tree.ts:86) and never sees the rules at all.

ELI5

Decisions

A plain JSON file, defaults for everything, and flags that never stick

Settings are a file you can read, diff, and carry to another machine.

decided
A JSON file, not SQLite. server/config.ts:7

A JSON file shows up in a diff, syncs with the rest of your dotfiles, and can be fixed in any editor when the page is not running. SQLite would need the dashboard, or a database tool, to read or change a setting. Not taken: SQLite.

decided
The file holds only what you change. shared/config.ts:94–96

Missing keys come from DEFAULT_CONFIG, so a first config can be one line and new keys added later need no migration. Not taken: writing every key on first run.

decided
--root and --port are for one run and are never saved. server/config.ts:12–13, :27–31

The settings page edits stored, the file without the flags, so Save after a --root run never replaces the folder the file already names. Only when the file has no folder yet does the page offer the --root one as a starting value (web/settings/Settings.tsx:79–80).

decided
A broken file warns and falls back to defaults. server/config.ts:50–54

A typo in a hand edit should not stop the server from starting. The warning names the file and the schema error.

decided
Hand edits apply without a restart. server/config.ts:66–77

The file is polled every second; after a 200 ms pause it reloads and only notifies when the parsed config actually changed. Reason for polling over an event watcher: not recorded.

decided
The server decides task, phase and workspace; the browser only reads them. server/scan.ts:74, :135–139

One place knows the folder rules. Not taken: sending the config to the browser and keeping a second parser in sync with it.

decided
Doc type order is the sort order. server/scan.ts:54–55, :78

The first matching type wins, and docs in a folder sort by their type's position, then file name. This replaces the two separate sort orders with one list you can reorder.

decided
Folders that miss the phase pattern still show, last. server/scan.ts:87–96, :38–47

A folder with something to read is never hidden by a strict pattern; it sorts after the numbered phases and is listed in the preview so you can fix the pattern.

decided
Saving needs a folder that exists; previewing does not need the dashboard page. server/routes/config.ts:9–22, :29

A config pointing nowhere would leave the dashboard empty, so it is rejected. Only Save writes, so only Save checks that the request comes from the dashboard page.

Risks and checks

Most mistakes are caught before Save, the rest by tests

A bad setting should never reach the scanner; the schema and the dry run stop it first.

What could go wrong

  • A phase pattern that does not compile, or has no num group, so no phase gets a number.
  • The docs folder is moved or deleted after it was saved.
  • The watcher reads the file halfway through a save.
  • A one-run --root overwrites the saved folder.
  • A custom layout silently leaves docs out.
  • A hand edit adds an unknown key, which then does nothing.

How the plan proves it didn't

  • Schema rejects both (shared/config.ts:7–17, :59).
  • No tree → the Setup screen asks again (web/App.tsx:49).
  • Temp file and rename (server/config.ts:59–61).
  • Settings edits stored, not current (server/config.ts:29).
  • Preview lists unmatched folders and skipped extensions (server/scan.ts:69, :96).
  • .strict() turns it into an error (shared/config.ts:65).

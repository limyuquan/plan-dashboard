Phase plan·plan-dashboard v1, phase 2·web/layout

Split one pane, and only that pane moves

The pane area stops being a grid of rows and becomes a tree of splits, like editor groups in VS Code. A split cuts one pane in two and leaves every other pane, and its size, alone. All layout rules move into one module of pure functions, the drop preview shows exactly what the drop will do, and the arrow keys move a tab to the pane that is really next to it on screen.

Written as the plan made before the build; file:line points at where each piece lands in web/layout/ (9 files, 903 lines by wc -l; 28 exports in model.ts by grep -c; 20 cases in model.test.ts, all passing under vitest run). The old rows-of-panes design is described from the phase brief; its code is not in this repository's history.

The short version

A layout becomes a tree, and one tidy-up rule keeps it honest

After this phase, every pane is a leaf in a split tree. Splitting, closing, dragging and the arrow keys all become pure functions over that tree.

2 · Adding a pane beside B

Start: A | B, which you had dragged to 70 / 30. Drop a doc on B's right edge.

ELI5

What changes

One pure model, thin views around it

The rules live in model.ts; the components only ask it questions and draw the answer.

model
web/layout/model.ts · the split tree and every operation on it · 337 lines

A layout is a Pane (tabs plus the one shown) or a Split (a direction, children, and sizes in percent) — web/layout/model.ts:10. Every operation returns a new tree plus which pane gets focus (Result, web/layout/model.ts:18), and every one that removes something ends in prune() (web/layout/model.ts:88), so the tidy-up rules exist exactly once.

tests
web/layout/model.test.ts · 20 cases over the pure functions · 155 lines

Each case builds a small tree, runs one operation, and compares the shape with sizes rounded (shape, web/layout/model.test.ts:38). No DOM and no React: the model is tested on its own.

view
web/layout/NodeView.tsx, SplitView.tsx · draw the tree recursively · 7 + 52 lines

NodeView picks a pane or a split (web/layout/NodeView.tsx:5). A split is a flex box whose children use their size as a flex-grow weight (web/layout/SplitView.tsx:45), so sizes never need to add up exactly. Dragging a divider re-splits only the two children either side of it (web/layout/SplitView.tsx:17).

view
web/layout/PaneView.tsx · one pane: tabs, actions, drop targets · 148 lines

Move and split buttons show only when they can do something (web/layout/PaneView.tsx:22). While dragging, edge bands appear only on sides with room (web/layout/PaneView.tsx:75), and the highlight is the exact half a new pane would take (web/layout/PaneView.tsx:62).

view
web/layout/TabStrip.tsx · one pane's tabs · 108 lines

Tabs drag to reorder or into another pane. The insertion line is counted without the dragged tab, which is where it really lands (web/layout/TabStrip.tsx:26), so the marker and the result agree here too.

drag
web/layout/dnd.ts, area.ts · drop routing and the pane area's size · 35 + 8 lines

drop() sends a doc or a tab to the right model call by zone (web/layout/dnd.ts:24); zonesFor() hides edges with no room and the no-op "only tab onto its own edge" (web/layout/dnd.ts:14). area.ts keeps the pixel size the room check needs (web/layout/area.ts:5).

keys
web/layout/Panes.tsx · the root, resize tracking, arrow keys · 53 lines

Ctrl/Option + arrow calls shift() (web/layout/Panes.tsx:12), which moves the shown tab to the real neighbour or splits a new pane that way. A ResizeObserver feeds the area size so the split buttons re-check their room (web/layout/Panes.tsx:36).

state
web/state/workspaces.ts, store.ts · callers, not rewritten

They switch from the grid helpers to the model: apply(Result) (web/state/workspaces.ts:29), first-visit seed() (web/state/workspaces.ts:47), and a load filter that drops any saved layout that is not a pane tree (web/state/store.ts:48).

ELI5

How it works

What you see is a tree, read left to right and top to bottom

A split says which way to cut and how big each piece is. Panes are the leaves.

Same tree as the expectation at web/layout/model.test.ts:63. rects() walks it to get each pane's box as fractions of the area (web/layout/model.ts:248); neighbour() and roomFor() both read those boxes.

Every action takes the same five steps

1 · input
Something asks for a change. A drop (web/layout/dnd.ts:24), an arrow key (web/layout/Panes.tsx:14), a pane button (web/layout/PaneView.tsx:36), or a sidebar click (web/state/workspaces.ts:97).
2 · model
One pure function builds the new tree. dropDoc, moveTab, moveToNewPane, shift, openTab, closeTab, closePane (web/layout/model.ts:136–237).
3 · tidy
prune() cleans up. Empty panes go, their space goes to the child before (else after), a one-child split becomes its child, and a split inside a same-direction split merges into it (web/layout/model.ts:55–90).
4 · store
apply() saves layout and focus together. web/state/workspaces.ts:29; layouts persist per workspace in the browser.
5 · draw
NodeView renders the tree. Splits become flex boxes with dividers, panes become tab strips and viewers (web/layout/NodeView.tsx:5).
ELI5

Decisions

Rules follow the screen, not the order panes were made in

Each decision removes a way for the picture and the result to disagree.

decided
A tree of splits, not a grid of rows. web/layout/model.ts:1–13

A tree can cut any one pane without touching the rest, which is the whole bug in case 1. Not taken: keeping rows and raising the 3 × 2 cap, which leaves the full-width-row problem in place.

decided
All tidy-up rules live in one prune(). web/layout/model.ts:55–90

Close, move and drop each just mark what changed and call it, so a closed pane's space is always handed out the same way. Not taken: tidying inside each operation, where the copies would drift.

decided
A new pane halves only the pane it splits. web/layout/model.ts:92–114

Sizes you set by hand survive adding panes. Not taken: equal shares on every add, the old behaviour in case 2.

decided
A minimum pane size instead of a pane count. web/layout/model.ts:20–24, web/layout/model.ts:198–205

Both halves of a split must be at least 280 px wide or 180 px tall, so the limit grows with the screen. Split buttons and drop edges ask the same check, so they never offer a split the model would refuse. First-visit layouts still stop at six panes.

decided
Neighbours by position on screen. web/layout/model.ts:268–299

A neighbour must share the edge in that direction; the one sharing the longest stretch wins. Not taken: index order, the old behaviour in case 3.

decided
The drop preview comes from the same zone as the drop. web/layout/PaneView.tsx:62–70, web/layout/dnd.ts:24–35

Hovering an edge paints exactly the half insertBeside creates; the centre paints the whole pane for "open here".

decided
Sizes are percentages drawn as flex weights. web/layout/SplitView.tsx:11–12

Rounding never leaves a gap or an overflow, and the model can stay in fractions with no pixel maths.

assumed
Old saved grids are dropped, not converted. web/layout/model.ts:325, web/state/store.ts:48–51, web/state/workspaces.ts:56–61

Layouts are per-browser view state. A saved layout that is not a pane tree fails isLayout and is skipped, and the workspace lays itself out again from its docs. Reason for not writing a converter: not recorded.

ELI5

Risks, checks, and done-when

Every risky rule gets a test, and the UI only offers what the model allows

The model is pure, so it is checked without a browser. The views are checked by hand.

What could go wrong

  • Closing a pane leaves a split with one child, or nested splits in the same direction, so sizes drift and dividers double up.
  • A split leaves a pane too small to read on a small window.
  • Dropping a pane's only tab onto its own edge does nothing but looks like it should.
  • A malformed or old-format saved layout crashes the first render.
  • Closing the last tab leaves no pane at all, so nothing can be dropped back in.
  • Paths go stale when a task folder moves from active/ to done/.

How the plan proves it didn't

  • collapses a split left with one child and merges same-direction splits; gives a closed pane its space to the pane before it (web/layout/model.test.ts:81–88).
  • refuses a split that would leave a half under the minimum size (web/layout/model.test.ts:73).
  • will not split a pane off its own only tab (web/layout/model.test.ts:69); zonesFor hides that edge (web/layout/dnd.ts:17).
  • rejects saved layouts that are not a pane tree, using the old {rows, heights} shape (web/layout/model.test.ts:152).
  • keeps one empty pane when everything is closed (web/layout/model.test.ts:94).
  • retargets tab paths after a task folder moves (web/layout/model.test.ts:147).
  • By hand: drag a divider, drop on each edge and the centre, and walk Ctrl/Option + arrows across a 2 × 3 layout.
One thing users will notice:

Pane arrangements saved by the old grid are not carried over. Each workspace re-lays itself out from its docs the first time it is opened after the update. No action is needed.
